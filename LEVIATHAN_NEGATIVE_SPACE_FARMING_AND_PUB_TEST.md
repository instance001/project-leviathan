# Leviathan Negative-Space Farming, Pressure-Driven Thread Hopping, and the Pub Test

**Status:** Working architecture hypothesis and experimental specification  
**Project context:** Project Leviathan / EF Engine / MCM / Relational Permutation / Cognitive Economy / connective-tissue architecture  
**Purpose:** Capture the emerging mechanism for pressure-driven thread activation, negative-space farming, candidate-C application, composition testing, and final adversarial coherence evaluation.

---

## Core Claim

Leviathan may not need a single component that "discovers the answer."

A cleaner architecture may be:

```text
pressure / mismatch / unresolved residue
↓
thread activation or hop
↓
EF Engine generates materially different mutations
↓
Negative-Space Farmer records what each mutation shows the answer is NOT
↓
complete C-field is preserved and tallied
↓
Cold C Applicator applies each C, and justified C-combinations, to the original problem
↓
survivors are handed to an independent final evaluator
↓
Pub Test / Sniff Test adversarially tries to knock each survivor over
```

The important structural separation is:

> **Farmer farms. Applicator applies. Critic attacks.**

No stage should quietly inherit the authority of another.

---

# 1. Pressure May Be What Makes the Threads Hop

The existing architecture already contains many candidate cognitive threads:

- relational comparison;
- deep recall;
- assumption review;
- semantic assimilation;
- imagination;
- cognitive economy;
- EF mutation and triangulation;
- contradiction handling;
- uncertainty handling.

The missing question is not necessarily:

> Where do the threads come from?

It may instead be:

> What causes one quiet thread to become active now?

A useful working hypothesis is that **pressure changes the activation topology**.

Possible pressure sources include:

```text
contradiction
uncertainty
failed prediction
resource scarcity
deadline / urgency
novelty
unresolved residue
boundary failure
transfer failure
memory insufficiency
repeated non-closure
```

A simple local shape:

```text
current thread proceeds
↓
pressure accumulates
↓
local threshold crossed
↓
BOOST another thread
DAMP current thread
↓
new thread rehydrates
↓
hop
```

This does not require a central executive that understands the whole system.

The trigger can be stupid and local.

> **Pressure detected → threshold crossed → boop → activation changes.**

---

## 1.1 Pressure Does Not Need to Create the Mechanism

The architecture should avoid the teleological idea that "need creates capability."

A safer formulation is:

> Pressure can create the conditions under which an already-available mechanism becomes necessary, visible, activated, reinforced, or retained.

In Leviathan:

```text
mechanism already exists
+
comfortable environment
=
mechanism may remain quiet

mechanism already exists
+
specific pressure
=
mechanism activates and becomes functionally visible
```

This makes pressure an experimental lever.

The same underlying problem can be tested under:

- no pressure;
- contradiction pressure;
- memory pressure;
- resource pressure;
- time pressure;
- incomplete information;
- competing task pressure.

Then compare thread trajectories.

---

## 1.2 Pressure Transducers

Some "boopers" may be better understood as **local pressure transducers**.

Their entire job:

```text
inspect narrow signal
↓
detect threshold crossing
↓
apply tiny gain change
↓
log intervention
```

Example:

```text
ContradictionPressureWatcher

input:
- expected relation
- observed relation

condition:
- contradiction strength > threshold

allowed action:
- BOOST relational comparison
- FLAG contradiction
- optionally DAMP current closure path

output:
- pressure event record
```

The watcher does not decide what the contradiction means.

It merely makes another thread more available.

# 2. The Gap Is Negative Space

Suppose Leviathan has a problem involving A and B.

The naive framing is:

```text
A + B
→ guess C
```

The stronger EF-compatible framing is:

```text
A + B
→ generate materially different mutations
→ observe what each mutation rules out
→ farm the negative space
```

The system is not asked:

> What is C?

It is first asked:

> What can C no longer be?

That difference is foundational.

---

# 3. The Negative-Space Farmer

The Negative-Space Farmer is not a gap detector and not a theory generator.

Its job is to harvest explicit **NOT-X** observations from EF mutation outcomes.

Example:

```text
mutation 01:
NOT temporal dependency

mutation 02:
NOT surface-form similarity

mutation 03:
NOT actor identity

mutation 04:
NOT resource quantity

mutation 05:
NOT ordering

mutation 06:
NOT surface-form similarity
```

The farmer converts these into a persistent field:

```text
NOT surface-form similarity   raw_count: 2
NOT temporal dependency       raw_count: 1
NOT actor identity            raw_count: 1
NOT resource quantity         raw_count: 1
NOT ordering                  raw_count: 1
```

These are **C-shaped exclusions**.

They describe the hole by describing what cannot occupy it.

---

## 3.1 Farmer Doctrine

> **Observe failed explanation → emit NOT-X → preserve → tally → hand off.**

The farmer must not:

- invent a positive C;
- rank one exclusion as "the answer";
- discard rare exclusions;
- collapse contradictory results;
- turn frequency into truth;
- repair failed explanations;
- rewrite the original problem;
- select a preferred worldview.

It farms **NOPE**.

That is all.

---

## 3.2 Negative-Space Record

A useful canonical record:

```text
NegativeSpaceRecord
- record_id
- original_problem_ref
- mutation_ref
- mutation_family
- mutation_seed
- tested_explanation
- exclusion_claim
- exclusion_scope
- supporting_observation_refs
- contradiction_refs
- confidence
- uncertainty
- independent_probe_group
- created_at
```

Example:

```text
exclusion_claim:
NOT explained by temporal ordering

scope:
under mutation family M17 and conditions Q

confidence:
0.81
```

The record is evidence, not truth.

---

# 4. Preserve Everything

No C-shaped exclusion is discarded merely because it is uncommon.

The correct answer may be:

- the highest-frequency exclusion;
- a medium-frequency exclusion;
- a single rare exclusion;
- a combination of exclusions;
- a boundary-specific exclusion;
- a C-set that only appears under one pressure regime;
- no unique C at all.

Therefore the field must preserve:

```text
dominant exclusions
recurring exclusions
rare exclusions
singletons
contradictions
unknowns
boundary-specific records
pressure-specific records
```

The tail matters.

The weird one-count C may be the bastard that actually explains the problem.

---

# 5. Frequency Is Evidence, Not Authority

Raw tally is useful, but tally alone is dangerous.

Ten near-identical EF mutations producing the same NOT-X are not equivalent to ten materially independent probes reaching the same result.

Therefore each C should carry at least:

```text
raw_count
independent_probe_count
mutation_family_spread
pressure_regime_spread
contradiction_count
```

Potential later fields:

```text
domain_spread
transfer_spread
boundary_spread
confidence_distribution
```

A better record might look like:

```text
NOT X

raw_count: 12
independent_probe_count: 3
mutation_family_spread: 3
pressure_regime_spread: 2
contradiction_count: 1
```

This prevents the system from farming its own echo.

# 6. The C-Field

After farming, the complete negative-space field is frozen.

Example:

```text
C01 = NOT temporal dependency
C02 = NOT actor identity
C03 = NOT surface-form similarity
C04 = NOT resource quantity
C05 = NOT ordering
C06 = NOT tool identity
C07 = NOT authority ownership
...
```

"C" here does not necessarily mean a hidden object.

A C may correspond to:

- a missing relation;
- a hidden condition;
- a timing dependency;
- a third actor;
- an omitted boundary;
- a resource interaction;
- a sequence constraint;
- a latent variable;
- a role relation;
- a combination of several factors;
- evidence that the A/B framing itself is wrong.

The system must therefore permit:

```text
NEGATIVE SPACE PRESENT
```

without forcing:

```text
THEREFORE A SINGLE THIRD THING EXISTS
```

Otherwise it will hallucinate invisible goblins every time two observations fail to close.

---

# 7. The Cold C Applicator

Once the C-field is frozen, a **separate agent** applies each candidate cold to the original problem.

This separation is critical.

The applicator should not inherit:

- farmer enthusiasm;
- farmer rank;
- tally;
- discovery order;
- narrative explanation;
- preferred interpretation.

Its first pass should see:

```text
original problem
+
candidate C
```

and nothing else required to bias it.

---

## 7.1 Blind First Pass

On the first application pass, hide tally.

Randomise candidate order.

Use opaque IDs.

Example:

```text
Candidate C17
Candidate C04
Candidate C22
```

The agent should not know:

```text
C17 occurred 1 time
C04 occurred 37 times
C22 occurred 9 times
```

because frequency creates a gravitational field.

The first question is purely structural:

> Does this candidate actually fit the original problem?

---

## 7.2 Applicator Output

A candidate can return:

```text
FIT
PARTIAL
FAIL
CONTRADICTION
UNKNOWN
```

A more detailed record:

```text
CandidateApplicationRecord
- application_id
- original_problem_ref
- candidate_c_ref
- fit
- explained_regions
- unexplained_regions
- contradictions
- boundary_conditions
- hidden_assumptions_detected
- uncertainty
- created_at
```

The applicator must not invent a replacement candidate when one fails.

Its job is application, not rescue.

---

# 8. There May Be More Than One C

The missing structure may be compositional.

Example:

```text
C = timing
```

or:

```text
C = timing + authority boundary
```

or:

```text
C = resource pressure + sequence + memory state
```

or:

```text
no stable single C
different regions require different C-sets
```

The true target may therefore be:

> **minimum surviving explanatory set**

rather than:

> one missing variable.

---

# 9. Bounded C-Composition

Brute-force composition is dangerous.

If there are 80 C candidates, testing every possible subset becomes combinatorial hell.

Therefore composition must be earned.

Example:

```text
C1 partially explains region X
C7 partially explains region Y

their failures are complementary
rather than redundant

→ permit C1 + C7 probe
```

This is where the Cognitive Economy Governor becomes important.

The governor should allow combinations only when there is evidence that composition may add material explanatory value.


# 10. Ablation of C-Combinations

A strong combined fit is not enough.

Each component must earn its place.

Suppose:

```text
C4 + C19 = strong fit
```

Then test:

```text
C4 alone
C19 alone
C4 + C19
```

Possible result:

```text
C4 alone     → PARTIAL
C19 alone    → PARTIAL
C4 + C19     → STRONG FIT
```

This suggests both may be load-bearing.

But:

```text
C4 alone     → STRONG FIT
C4 + C19     → STRONG FIT
```

suggests C19 may be decorative baggage.

This protects Leviathan from producing baroque explanations containing many technically compatible but unnecessary components.

---

# 11. Failed Application Becomes New Negative Space

Nothing is thrown away.

If:

```text
C12 applied to A/B
→ fails under condition Q
```

that failure is new evidence.

It can return to the negative-space field.

The loop becomes:

```text
farm negatives
↓
apply candidates
↓
observe fit / failure
↓
farm application failures
↓
narrow surviving space
↓
compose where justified
↓
repeat
```

This is consistent with EF.

The system repeatedly removes what cannot occupy the gap.

---

# 12. Sculpting C

A useful metaphor:

> Leviathan does not guess C.

It **sculpts C by removal**.

```text
candidate space
↓
NOT this
↓
NOT that
↓
NOT under these conditions
↓
NOT unless combined with X
↓
NOT across this boundary
↓
surviving structure
```

The remaining form becomes increasingly difficult to avoid.

That is a stronger basis for a candidate than fluent positive generation.

# 13. The Final Evaluator

After cold application and justified composition, surviving C candidates move to a third epistemically isolated stage.

This final evaluator should receive:

```text
original problem
+
one candidate C
```

or:

```text
original problem
+
one candidate C-set
```

It should not receive:

- tally;
- rank;
- farmer history;
- applicator enthusiasm;
- other competing candidates;
- narrative provenance unless needed for exact evidence inspection.

Its role is adversarial.

---

# 14. The Sniff Test / Pub Test

The final evaluator is not another discovery engine.

It is the **sniff test**.

Human-facing framing:

> Put the claim on the table in front of a smart, skeptical outsider with no emotional investment in it.

Ask:

> Does this actually hold, or does it smell like bullshit?

The ideal evaluator attitude is not:

> "How can I improve this?"

It is:

> "How can I break this?"

---

## 14.1 Grok-Repo Analogy

The desired behaviour is similar to handing a repository or paper to a skeptical outsider and asking:

> Honest thoughts?

Useful outcomes include:

```text
"This is rubbish.
The claim does not follow.
The architecture is hand-waving.
This would not work realistically."
```

or:

```text
"I tried to knock the central claim over.
I cannot currently disprove it.
The logic holds under the presented conditions.
This is a serious statement."
```

The second outcome is meaningful precisely because the evaluator was trying to reject the claim rather than flatter it.

---

# 15. Formal Name and Human Name

Suggested formal name:

> **Adversarial Coherence Gate**

Suggested human-facing names:

> **Pub Test**

> **Sniff Test**

The human names communicate the function better.

The formal definition:

> **An adversarial coherence gate whose purpose is to reject explanations that are locally plausible but globally fail against the original problem.**

---

# 16. Sniff-Test Questions

For each candidate or C-set:

```text
Does this explain the important observations?

Does it smuggle in assumptions?

Does it contradict the original problem?

Does it leave major residue unexplained?

Does it rely on circular reasoning?

Does it require special pleading?

Does every component in the C-set do real work?

Does it survive obvious counterexamples?

Does it remain coherent when stripped of internal jargon?

Does it hold under the weakest point I can identify?

Would I be embarrassed to let this claim out of the lab?
```

The final question is deliberately crude.

It captures the "pub test" spirit.

---

The evaluator should be boring.

Example:

```text
AdversarialCoherenceRecord

- uncertainty

```

Suggested verdicts:

```text
SURVIVES
PARTIAL
FAILS
UNRESOLVED
```

The evaluator must not repair the candidate.

If it fails:

```text
FAILS
```

Back down the conveyor.

Stay in your chair.

---

# 18. Necessity Testing at the Pub Test

For combinations, the final evaluator should also ask:

> Is every component necessary?

Example:

```text
C4 + C19
```

The evaluator may test:

```text
remove C4
remove C19
preserve both
```

A strong combination should show that each component contributes material explanatory value.

Otherwise the combination is overfitted decoration.

---

# 19. Reunification Happens Only After Isolation

Only after all adversarial evaluations are frozen should the larger system reunite:

- farmer tallies;
- independent-probe counts;
- application results;
- combination results;
- ablation results;
- pub-test verdicts.

Then the system can compare:

```text
C1
farmer tally: HIGH
cold application: FIT
pub test: FAIL

C7
farmer tally: LOW
cold application: FIT
pub test: SURVIVES

C12 + C31
farmer tally: MEDIUM + LOW
cold application: STRONG FIT
pub test: SURVIVES
ablation: BOTH REQUIRED
```

This prevents popularity from becoming truth.

The weird singleton can win.

The obvious high-frequency candidate can lose.

# 20. Why Epistemic Separation Matters

Each stage deliberately knows less than the whole system knows.

That is a feature.

```text
Farmer:
knows mutation outcomes
does not know final answer

Applicator:
knows original problem + candidate
does not know tally or farmer preference

Pub Test:
knows original problem + candidate
does not know discovery history or candidate popularity
```

This follows the Leviathan doctrine:

> **Local competence, aggressively bounded awareness.**

Information isolation acts as experimental control.

Detects local non-closure or pressure and alters activation.

# 25. Failure Modes to Guard Against

## Tally Worship

High occurrence becomes assumed truth.

**Countermeasure:** blind first application pass.

## Rare-Candidate Deletion

Low-frequency C is discarded.

**Countermeasure:** preserve all C records.

## Farmer Becomes Theorist

Negative-space farmer starts inventing positive explanations.

**Countermeasure:** farmer may only emit exclusions and evidence.

## Applicator Becomes Repair Agent

Failed C is silently modified.

**Countermeasure:** fail and hand back.

## Critic Becomes Collaborator

Pub-Test agent tries to improve a weak candidate.

**Countermeasure:** evaluator attacks only.

## Combinatorial Explosion

Every C is combined with every other C.

**Countermeasure:** composition must be earned by complementary partial fits.

## Decorative C-Sets

Large combinations fit but contain unnecessary components.

**Countermeasure:** component ablation.

## Mutation Echo

Many near-identical EF mutations inflate tally.

**Countermeasure:** independent-probe and mutation-family counts.

## Premature Closure

One strong candidate suppresses remaining field.

**Countermeasure:** preserve full negative-space dataset and complete isolated evaluation.

## Single-C Bias

Architecture assumes one missing variable.

**Countermeasure:** permit multi-C closure and unresolved/no-unique-C outcomes.

# 26. Experimental Questions

1. Does pressure reliably alter thread activation trajectories?
2. Which pressure classes wake which threads?
3. Does negative-space farming produce more robust candidates than direct positive generation?
4. Does blind application change candidate ranking compared with tally-aware application?
5. How often does the lowest-frequency C survive while high-frequency C's fail?
6. How often are multiple C's jointly required?
7. How often does ablation reveal decorative components?
8. Does the Pub Test reject candidates that earlier stages rated highly?
9. Does adversarial isolation reduce self-confirming reasoning loops?
10. Does preserving all failed C's improve future investigations?
11. Can the system converge without forcing a unique C?
12. What proportion of final survivors are singletons versus compositions?
13. Does pressure-regime diversity improve negative-space quality?
14. Which stages add genuine information versus merely restating earlier evidence?
15. Can a cheap local pressure transducer reliably trigger useful thread hops?
16. Does the whole pipeline outperform a single model simply asked to "reason deeply"?

# 29. Closing Position

The emerging mechanism is not:

> "guess the hidden answer."

It is:

> **create pressure, expose non-closure, mutate the problem, farm exclusions, preserve the whole negative field, apply candidate structures cold, compose only where earned, ablate unnecessary parts, and finally hand each survivor to a skeptical outsider whose only job is to say whether it actually fucking holds.**

That is a much more Leviathan-shaped route to C.
